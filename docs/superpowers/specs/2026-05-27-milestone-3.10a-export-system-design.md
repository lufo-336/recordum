# Milestone 3.10a — Export System — Design

> **Status:** approved design, pre-plan. Part of roadmap Milestone 3.10 (Export + Backup/Restore), **split** into 3.10a (Export, this doc) and 3.10b (Backup/Restore, later). Backup/restore is explicitly out of scope here.

## 1. Goal

Let the user export their habit data in five formats — **PDF, HTML, Markdown, JSON, CSV** — from two subjects: a **single habit** (from its Detail screen) and the **whole library**. JSON/CSV are full-fidelity data dumps; PDF/HTML/Markdown are human-readable reports (metadata + summary stats + completion table + a rendered year-heatmap image).

The export formatters are the **second real consumer of the plugin system**: a first-party `Recordum.Plugins.ExportEngine` assembly registers one formatter per format under the existing `export.format` extension point, mirroring how the Chart Engine (M3.9) piloted `chart.renderer`. The WPF export dialog resolves a formatter through `IExtensionPointRegistry` and never references the engine directly.

## 2. Scope

**In scope:** 5 formatters; single-habit + whole-library subjects; date-range filter; section toggles via `ExportTemplate.LayoutJson` (honoring the 4 seed templates as presets, no template-builder UI); heatmap PNG embedded in HTML/PDF; an `ExportJob` history row per export; a modal export dialog launched from the Habit Detail screen and a library-export command.

**Out of scope (deferred):** Backup/restore (3.10b); trend/hourly charts in reports (heatmap only this cut); a template-builder UI; arbitrary multi-habit selection; async/background export queue; scheduled/recurring exports.

## 3. Architecture

Five projects touched, one new:

| Project | Role |
|---|---|
| `Recordum.Plugins.Contracts` | `IExportFormatter` extension contract + `ExportModel` DTO + `ExportLayout` (parse of `LayoutJson`). UI-free, plain `net10.0`. |
| `Recordum.Core` | `ExportSubject` enum only (simple enum, referenced by both Contracts and Data; no new deps). |
| `Recordum.Data` | `ExportRequest` record + `IExportQueryService.BuildAsync(ExportRequest) → ExportModel` + `IExportJobService` (record/list history). |
| **`Recordum.Plugins.ExportEngine`** (NEW, `net10.0`, no WPF) | 5 `IExportFormatter` impls + QuestPDF + headless SkiaSharp heatmap renderer + `ExportEngineActivator` (registers under `export.format`). Sole home of QuestPDF. |
| `Recordum.WPF` | `ExportDialogViewModel` + view, launch points, DI, save-file, i18n. |

**Deviation (documented):** like `IChartQueryService` (M3.9), `IExportQueryService` lives in **`Recordum.Data`, not Core**, because it returns `ExportModel` (a `Plugins.Contracts` type) and Core has zero non-Core dependencies. `Recordum.Data` already references `Plugins.Contracts`.

The Export Engine is plain `net10.0` (not `-windows`): QuestPDF and SkiaSharp (core) render headlessly without WPF, so Phase 4 (web) can reuse the engine unchanged.

## 4. Contract (`Recordum.Plugins.Contracts/Export`)

```csharp
// ExportModel.cs — UI-free description of what to export.
public sealed record ExportModel(
    ExportSubject Subject,           // SingleHabit | Library
    string Title,                    // habit name, or "Recordum Library"
    DateOnly From, DateOnly To,
    DateTimeOffset GeneratedAt,
    IReadOnlyList<ExportHabitModel> Habits);

public sealed record ExportHabitModel(
    Guid HabitNodeId, string Name, string HabitType, string? Color,
    ExportSummary Summary,
    IReadOnlyList<ExportCompletionRow> Completions,   // included if Completions section on
    IReadOnlyList<ExportNoteRow> Notes,               // included if Notes section on
    IReadOnlyList<ExportHeatmapCell> Heatmap);        // (week,weekday,step 0-4); empty if Heatmap section off

public sealed record ExportSummary(int CurrentStreak, int LongestStreak, int TotalCompletions, decimal? GoalActual, decimal? GoalTarget);
public sealed record ExportCompletionRow(DateTimeOffset CompletedAt, decimal? Value, string? Metric, bool Retroactive);
public sealed record ExportNoteRow(DateTimeOffset UpdatedAt, string BodyMd);
public readonly record struct ExportHeatmapCell(int Week, int Weekday, int Step);
```

```csharp
// IExportFormatter.cs — extension under WellKnownExtensionPoints.ExportFormat ("export.format").
public interface IExportFormatter : IExtensionPoint
{
    ExportFormat Format { get; }                 // existing Core enum: Pdf|Html|Markdown|Json|Csv
    bool CanFormat(ExportFormat format);
    byte[] Write(ExportModel model);             // bytes so PDF/PNG and text formats are uniform
}
```

```csharp
// ExportLayout.cs — typed view of ExportTemplate.LayoutJson (like ChartConfig).
public sealed record ExportLayout(
    bool Metadata = true, bool Summary = true, bool Heatmap = true,
    bool Completions = true, bool Notes = true, string Range = "all")
{
    public static ExportLayout Parse(string? json);   // malformed/empty → defaults
    public string ToJson();
}
```

`Write` returning `byte[]` keeps Contracts UI- and IO-free; the host owns file IO. `ExportSubject` lives in Core (so `ExportRequest` can reference it without depending on Contracts).

## 5. Data layer (`Recordum.Data`)

```csharp
// Core: ExportSubject.cs
public enum ExportSubject { SingleHabit, Library }

// Data: ExportRequest.cs (lives in Data — references ExportLayout, a Contracts type; Core has no Contracts dep)
public sealed record ExportRequest(ExportSubject Subject, Guid? HabitNodeId, DateOnly From, DateOnly To, ExportLayout Layout);

// Data: IExportQueryService
public interface IExportQueryService
{
    ValueTask<ExportModel> BuildAsync(ExportRequest request, CancellationToken ct = default);
}
```

`ExportQueryService` assembles the model:
- **Subject = SingleHabit:** load the node; build one `ExportHabitModel`.
- **Subject = Library:** all non-deleted habit nodes (skip groups for stats; groups may appear as headers later — not this cut).
- **Summary:** `IStreakAggregator` (current/longest), completion count, `IGoalService` actual/target.
- **Completions/Notes:** `ICompletionService.ListByHabitAsync` / `INoteService.ListByHabitAsync`, filtered to `[From,To]`, only if the section is enabled.
- **Heatmap cells:** reuse the M3.7 logic — `GetHeatmapAsync`/`GetDailySumAsync` + `IIntensityRampResolver` to produce `(week, weekday, step)` triples; empty when the Heatmap section is off.
- **Range:** the query service always uses the already-resolved `ExportRequest.From/To`. The **dialog** seeds those from `ExportLayout.Range` (`"all"` → earliest data…today; `"30d"`/`"90d"`/`"1y"` → relative to today via `IClock`) or from a custom range the user enters. This keeps range interpretation in one place (the UI) and the query service purely data-driven.

`IExportJobService.RecordAsync(ExportJob)` writes a history row (`Format`, `FilePath`, `FilterJson`, `GeneratedAt`, optional `ExportTemplateId`); `ListAsync` returns recent jobs ordered by `GeneratedAt DESC`. **No schema change** — `export_job`/`export_template` exist since InitialSchema; `schema_version` stays `2.6`.

## 6. Export Engine (`Recordum.Plugins.ExportEngine`)

New assembly, `net10.0`, `ImplicitUsings`/`Nullable` on, `NoWarn=NU1701` if a transitive TFM warning surfaces. References `Recordum.Core` + `Recordum.Plugins.Contracts`. Packages: **QuestPDF** (Community license), **SkiaSharp**.

- `plugin id = io.recordum.export-engine`; manifest declares `extension_points: ["export.format"]`.
- **Five formatters**, each `IExportFormatter` with its own `Format`/`CanFormat`:
  - `JsonExportFormatter` — `System.Text.Json` serialization of `ExportModel` (full fidelity, indented).
  - `CsvExportFormatter` — completion rows flattened (habit, date, value, metric, retroactive); RFC-4180 quoting.
  - `MarkdownExportFormatter` — headings + summary list + completion table; heatmap as a compact text table fallback (or a linked PNG sidecar is out of scope — inline table).
  - `HtmlExportFormatter` — self-contained HTML; heatmap embedded as `data:image/png;base64,…`.
  - `PdfExportFormatter` — QuestPDF document; heatmap embedded as a rendered image.
- `HeatmapImageRenderer` — headless SkiaSharp: draws the 53×7 grid with the 5-step GitHub ramp (light palette; export is print-oriented) → PNG `byte[]`. Shared by HTML + PDF.
- `ExportEngineManifest` + `ExportEngineActivator` (idempotent — short-circuits if formatters already registered, like `ChartEngineActivator`). Sets `QuestPDF.Settings.License = LicenseType.Community` once on activation. Registers all five under `WellKnownExtensionPoints.ExportFormat`.
- Wired into `ServiceRegistrar` (`IExportEngineActivator` singleton, `IExportQueryService`/`IExportJobService` scoped) and activated in `ApplicationInitializer` after migrations (alongside the Chart Engine).

## 7. WPF

- `ExportDialogViewModel` (transient): inputs = subject (pre-set when launched from a habit), `ExportFormat`, `ExportTemplate` (drives `ExportLayout` section toggles, user-overridable), date range. `ExportCommand`:
  1. resolve formatter: `registry.GetExtensions(ExportFormat).OfType<IExportFormatter>().FirstOrDefault(f => f.CanFormat(SelectedFormat))`;
  2. `model = await query.BuildAsync(request)`;
  3. `bytes = formatter.Write(model)`;
  4. write to the path from a Save-file dialog (abstracted behind `ISaveFileDialog` for testability);
  5. `await jobs.RecordAsync(...)`.
- `ExportDialog` view (modal) + `IExportDialogLauncher` (DI-injectable, mirrors `IHabitTemplatePickerLauncher`) so tests drive it headlessly.
- Launch points: an **Export** button on the Habit Detail screen header (pre-targets the current habit, `Subject=SingleHabit`); an **Export library** entry in the top nav / Settings (`Subject=Library`).
- File IO and the OS save dialog stay in WPF; the engine and query service remain IO-free.
- All user strings in `Strings.resx` + `Strings.it.resx` (English-first), manual designer additions per the M3.7+ pattern.

## 8. Testing

TDD throughout (red → green → commit per task):
- **Contract:** `ExportLayout.Parse` round-trip + malformed-defaults.
- **Formatters (engine):** per-format unit tests — JSON deserializes back to an equivalent model; CSV has expected header + row count + quoting; Markdown/HTML contain expected sections and (HTML) a `data:image/png;base64` heatmap; PDF produces non-empty bytes starting with `%PDF`. `HeatmapImageRenderer` returns a valid PNG (`\x89PNG` magic).
- **Activator:** registers 5 formatters under `export.format`; idempotent on repeat.
- **Data:** `ExportQueryService` integration over `DbFixture` — single-habit vs library, section toggles include/exclude completions/notes/heatmap, range filtering, summary numbers. `ExportJobService` record/list.
- **WPF:** `ExportDialogViewModel` tests with fakes (formatter resolution, section toggles from template, save path, `ExportJob` recorded) using a `FakeSaveFileDialog`.
- **E2E smoke:** real `ExportEngineActivator` + registry → for each `ExportFormat`, resolve the formatter and produce non-empty bytes from a seeded model.

## 9. Dependencies & licensing

- **QuestPDF** — Community license (free for the project's scale; open-source). License set programmatically at engine activation. Sole consumer is the Export Engine.
- **SkiaSharp** — already present transitively via LiveCharts; used directly for the heatmap PNG.

## 10. Known limits / deferred

- Reports embed the **heatmap only**; trend/hourly charts deferred.
- Markdown heatmap is a text-table fallback (no inline image) to keep `.md` self-contained and diff-friendly.
- Library export lists habits flat (group hierarchy headers deferred).
- No background/async export; synchronous on a reasonable Phase-3 dataset.
- Template **builder** UI deferred; users pick among existing/seed templates.
- Backup/restore is **3.10b**.
