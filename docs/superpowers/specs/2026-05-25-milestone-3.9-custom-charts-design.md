# Milestone 3.9 — Custom Charts + Chart Engine pilot

> Design doc. Status: **approved 2026-05-25**. Next: implementation plan via writing-plans.
> Authoritative sources it must respect: roadmap §7 (Fase 3 milestones), plugin spec §8.3 (Chart Engine come core plugin pilota), DesignBrief (visual language), DatabaseSchema v2.2 (no invasive migrations after Fase 3).

## 1. Goal

Ship **user-defined custom charts** rendered by a **Chart Engine** that is the first real consumer of the plugin API: it registers an `IChartRenderer` extension under the `chart.renderer` extension point and is resolved by the host through the `ExtensionPointRegistry` — never referenced directly by the charts UI. This validates the Fase-3 plugin contract end to end (manifest → enable → register → consume) before any third-party runtime exists (Fase 7).

Secondary goal: migrate the four bespoke M3.7 detail charts to LiveCharts2 so all chart rendering shares one library.

## 2. Decisions (settled)

| Topic | Decision |
|---|---|
| Is the Chart Engine a plugin? | **Yes** — full extension-point indirection. Settled by roadmap §7 + plugin spec §8.3. Not re-litigated. |
| Where do custom charts live? | **New top-level "Charts" workspace** (peer of Home), gallery + builder. Cross-habit charts are app-level; `chart_series` already supports series from different `HabitNode`s. |
| Migrate M3.7 detail charts? | **All four** to LiveCharts2 — with a visual-parity guardrail (see §7). |
| Chart types in scope | **Line, Bar, Area, StackedBar, Scatter, Pie** (full gallery). |
| Architecture | **Approach A**: separate `Recordum.Plugins.ChartEngine` assembly + UI-agnostic data-DTO contract. |
| Chart library | **LiveCharts2** (`LiveChartsCore.SkiaSharpView.WPF`, MIT) via NuGet, referenced only by the ChartEngine assembly. |
| Schema delta | **Zero.** `chart`/`chart_series` exist since InitialSchema; `ConfigJson` holds per-chart config. `schema_version` stays `2.6`. |

## 4. The `chart.renderer` contract

Lives in `Recordum.Plugins.Contracts`, **UI-agnostic** (no WPF types) so Core/Data continue to reference Contracts without a UI dependency.

```csharp
public enum ChartKind { Line, Bar, Area, StackedBar, Scatter, Pie }

public interface IChartRenderer : IExtensionPoint {
    bool CanRender(ChartKind kind);
    object CreateView(ChartRenderModel model);   // WPF impl returns a FrameworkElement; host casts
}

public sealed record ChartRenderModel(
    ChartKind Kind,
    string? Title,
    IReadOnlyList<ChartSeriesModel> Series,
    ChartAxisModel? XAxis,
    ChartAxisModel? YAxis,
    ChartThemeModel Theme);

public sealed record ChartSeriesModel(string Label, string? ColorHex, IReadOnlyList<ChartPoint> Points);
public readonly record struct ChartPoint(double X, double? Y, string? Label);
// cartesian (line/bar/area/stacked/scatter): X numeric (or index) + Y
// categorical (pie): one ChartPoint per slice, Label set, Y = value

public sealed record ChartAxisModel(string? Label, bool IsTime, string? Format);
public sealed record ChartThemeModel(bool IsDark, string TextColorHex, string GridColorHex);
```

`object CreateView(...)` returning the platform view (FrameworkElement in WPF) is the **documented Fase-3 limitation** that keeps Contracts UI-free. Fase 7 may introduce a typed view envelope without breaking first-party code.

`ChartKindParser` maps the `Chart.ChartType` string column (`"line"`, `"bar"`, `"area"`, `"stacked-bar"`, `"scatter"`, `"pie"`) ↔ `ChartKind`. Unknown string → `Line` fallback (logged).

## 5. Data flow

1. Workspace loads saved `Chart`s via `IChartService.ListAsync()`.
2. On selection: `IChartQueryService.BuildModelAsync(chartId, range, isDark, ct)`:
   - Loads `Chart` + `ChartSeries[]` via `IChartService.GetAsync`.
   - Parses `Chart.ConfigJson` → `ChartConfig` (range preset/custom from-to, bucket daily/weekly, legend, axis labels).
   - For each `ChartSeries`: resolve `HabitNode` + optional `MetricDefinition` → time-series points over the range, reusing `ITrendQueryService` (bucketing, metric-aware) / `ICompletionService.GetDailySumAsync`. Pie/categorical: aggregate each series to a single total → one `ChartPoint`.
   - Maps `ChartType` → `ChartKind` via `ChartKindParser`.
   - Builds `ChartThemeModel` from current theme (dark/light text + grid colors).
   - Returns `ChartRenderModel`.
3. Workspace resolves the renderer: `ExtensionPointRegistry.GetExtensions(WellKnownExtensionPoints.ChartRenderer)`, casts each to `IChartRenderer`, picks the first where `CanRender(kind)`, calls `CreateView(model)`, casts the result to `FrameworkElement`, hosts it in a `ContentControl`. **This is the full plugin path — the pilot.**

### `ChartConfig` (serialized into `Chart.ConfigJson`)

```csharp
public sealed record ChartConfig(
    string Range,            // "30d" | "90d" | "1y" | "custom"
    string? FromIso, string? ToIso,   // when Range == "custom"
    string Bucket,           // "daily" | "weekly"
    bool ShowLegend,
    string? XAxisLabel, string? YAxisLabel);
```
Default when `ConfigJson` is empty/`{}`: `Range="90d", Bucket="daily", ShowLegend=true`. Schema delta zero.

### Provenance

User-built charts: `created_by_plugin_id = null` (the renderer renders, it does not own the data). The `io.recordum.chart-engine` plugin id appears only as the renderer's `PluginId`, never on persisted `Chart` rows. No provenance complications.

**Plugin id, canonical:** `io.recordum.chart-engine` everywhere — manifest `id`, `ChartEngineRenderer.PluginId`, and the `ExtensionRegistration.PluginId`. These three must be byte-identical (registry/`PluginManager` key on the string). The plugin spec's note about synthetic `core.*` ids concerns `IPluginContext.PluginId` for provenance, which 3.9 does not exercise (user charts are user-owned), so it does not apply here.

## 6. Chart Engine plugin (`Recordum.Plugins.ChartEngine`)

- `ChartEngineRenderer : IChartRenderer` — `PointId = ChartRenderer`, `PluginId = "io.recordum.chart-engine"`. `CanRender` returns true for all six kinds. `CreateView` builds `CartesianChart` (line/bar/area/stacked/scatter) or `PieChart` (pie) in **code** (no LiveCharts XAML namespaces leak into WPF). The `ChartRenderModel → ISeries[]` mapping is a **public pure method** (`MapSeries`) so it can be unit-tested without instantiating a control.
- `ChartEngineManifest` — a `PluginManifest` (`id = "io.recordum.chart-engine"`, `extension_points: ["chart.renderer"]`, type `plugin`, publisher Recordum).
- `ChartEngineActivator` — registers the renderer into `IExtensionPointRegistry` and calls `IPluginManager.EnableAsync(manifest)`. Invoked by `ApplicationInitializer` after migrations. **Exercises manifest → enable → register → consume.**
- Detail-chart builders (LiveCharts2 view factories consumed by WPF controls in §7): `TrendChartBuilder`, `HourlyChartBuilder`, `YearHeatmapBuilder`, `StreakTimelineBuilder`. Trend/Hourly build from `ChartRenderModel` via the renderer's mapping; heatmap/timeline use dedicated builders (non-cartesian).
- NuGet `LiveChartsCore.SkiaSharpView.WPF` (MIT). Referenced only here; WPF gets it transitively.

It is acceptable for the host app (`Recordum.WPF`) to reference this first-party in-process plugin assembly at compile time — Fase-3 first-party plugins are compiled in. Fase-7 third-party plugins run in WebView2 with no such reference.

## 7. WPF Charts workspace + detail migration

### Top-level workspace nav
- A **Home | Charts** workspace switch at the top of `MainWindow`. `Ctrl+4` → Charts (existing `Ctrl+1/2/3` remain Home sub-tabs and imply the Home workspace). `TimerStatusBar` persists across workspaces.
- When Charts is active, the `Home | HabitScreen | Editor` pane area is replaced by `ChartsView`. `MainWindowViewModel` gains a `CurrentWorkspace` enum (Home | Charts).

### ViewModels
- `ChartsWorkspaceViewModel` — list of `ChartListItemViewModel`, `SelectedChart`, New/Delete chart, hosts the rendered view (a `FrameworkElement` property bound to a `ContentControl`), triggers `BuildModelAsync` + renderer resolution on selection / builder save.
- `ChartListItemViewModel` — name, kind, series count.
- `ChartBuilderViewModel` — edit Name, `ChartKind` (combo of 6), range/bucket, series list (add/remove/reorder; each: pick `HabitNode`, optional `MetricDefinition`, label, color). Save via `IChartService.CreateAsync`/`UpdateAsync` + `ReplaceSeriesAsync`.

### Views
- `ChartsView.xaml` — master (chart list, 220px) | detail (rendered chart `ContentControl` + collapsible builder panel).

### Detail chart migration (4 controls)
`TrendChartControl`, `HourlyHistogramControl`, `YearHeatmapControl`, `StreakTimelineControl` keep their **public API / dependency properties unchanged** (M3.7 detail ViewModels are NOT touched). Only the internal rendering swaps from `Canvas`+shapes to a LiveCharts2 view built by a ChartEngine builder.

⚠️ **Visual-parity guardrail (honest risk).** Year heatmap (GitHub-style 53×7 calendar, 5-step ramp) and streak timeline (range bars) are bespoke visuals where the DesignBrief is authoritative. LiveCharts2 `HeatSeries`/`RowSeries` may **degrade** that look. Plan: attempt all four against a visual-parity bar; **if heatmap and/or timeline cannot match the brief, those control(s) stay on the existing `Canvas` implementation** — decision recorded in the milestone status, never silent. Trend + Hourly migration is an unambiguous win (interactivity, consistency) and is not at risk.

## 8. Testing

- **Data** `ChartQueryServiceTests`: model-building correctness — point resolution, metric resolution + missing-metric fallback, range/bucket, pie aggregation, multi-series, empty chart. Pure, high value.
- **ChartEngine**: `CanRender` for all 6 kinds; `MapSeries` (`ChartRenderModel → ISeries[]`) as a pure testable method; `ChartKindParser` round-trip + unknown fallback.
- **Plugins**: `ChartEngineActivator` registers `IChartRenderer` under `core.chart-engine`; `GetExtensions(ChartRenderer)` returns it; `CanRender` reachable through the registry.
- **WPF**: `ChartsWorkspaceViewModel` + `ChartBuilderViewModel` (selection, CRUD, series add/remove/reorder, save round-trip). E2E STA smoke: workspace resolves a renderer and produces a non-null `FrameworkElement`. STA smoke: each of the 4 detail controls constructs with its LiveCharts2 internals.

## 9. i18n

New resx keys (en + it, designer regenerated): workspace title, New/Delete chart, builder fields (Name/Type/Range/Bucket/Series/Add series/Habit/Metric/Color), the 6 chart-kind labels, empty states (no charts / no series). All user-facing strings English-first.

## 10. Out of scope (YAGNI for 3.9)

- Dashboard widgets (`dashboard.widget` extension point) — separate concern.
- Chart export (PDF/PNG) — lands with Export System (M3.10).
- Custom color palettes / per-point styling beyond per-series color.
- Real-time chart refresh on completion events (charts refresh on open/save; an `IEventBus` live-refresh can come later if needed).
- WebView2 / typed view envelope for the renderer (Fase 7).
