# Milestone 3.5 — Completion Recording Design

> **Status:** Approved 2026-05-21. Authoritative for the M3.5 implementation plan. Conflicts with `Recordum_ProductSpec_v2.docx` are deliberate scope choices and called out in §10.

## 1. Goal

Ship the surface that lets users **record, edit, and review completions** for every habit type. Completion entry has two paths from Home: a per-row quick-action icon (instant or near-instant entry) and a row-click that opens a new `HabitScreen` (right pane, sibling to `EditorPane`) hosting a 90-day heatmap, recent completions list, quick-add form, and timer controls. A new bottom status bar on `MainWindow` keeps active timers always visible. The Streak Engine is out of scope (M3.8) — M3.5 emits events via `IEventBus` that M3.8 will consume.

## 2. Scope

**In scope:**
- Completion recording for all five `HabitType`s (Action, Counter, Resistance, Journal, State) plus session mode (Counter with `TimerMode=Session`).
- Multi-series semantics: one `Completion` per session, multiple `CompletionValue` rows differentiated by `SeriesIndex` (0..N-1). For session mode, `CompletionSegment[]` rows mirror the `SegmentDefinition` ones.
- Quick-action icon per row in Home (per habit type — see §6).
- New `HabitScreen` right pane (sibling to `EditorPane`) with 90-day heatmap, recent completions list, quick-add form, timer controls. Row-click opens it.
- Retroactive completion: click any past day on the heatmap → opens quick-add for that date. No date constraints (any past day from habit creation onwards; future dates blocked).
- Timer state machine + recovery via new `active_timer` table (schema delta v2.5). App restart → unfinished timers reattach.
- Always-visible `TimerStatusBar` at the bottom of `MainWindow` listing every active timer, with HH:MM:SS, Pause/Resume, Stop. Multi-timer supported.
- `IEventBus` emit on every write: `CompletionRecorded` / `CompletionUpdated` / `CompletionDeleted`.
- Edit/delete completion from `HabitScreen`'s completion list (inline or via a small dialog).
- Journal completion via plaintext multiline `TextBox`; `WebView2` + Toast UI/Milkdown comes in M3.6.

**Out of scope (deferred — explicit):**
- Streak Engine and any `current_streak` UI surface (M3.8). M3.5 only emits events.
- Charts, distributions, statistics on completions (M3.7 + M3.9).
- Markdown editor for Journal (M3.6).
- Notification firing/reminders (notifications row CRUD already shipped in M3.4; runtime scheduler deferred).
- Drag-to-reorder series, attachments upload on completion (M3.6 / M3.7).
- Streak/goal preview inside `HabitScreen` (placeholders only; M3.7/M3.8 fill them).
- Bulk completion (multi-day select on heatmap) — single-day click only.

### 3.1 MainWindow layout

5-column root grid plus a new bottom `RowDefinition` for the timer status bar:

```

│ HomeView (*)  │ S │ HabitScreen (520)  │ S │ EditorPane (480, optional)        │
```

### 3.2 Row interaction (Home)

| Trigger | Action |
|---|---|
| Click anywhere on row (not on icon, rename TextBox, context-menu chrome) | Opens `HabitScreen` for that habit. `HomeViewModel.SelectedRow` already exists from M3.4 — semantics reused. |

> **Migration of M3.4 trigger:** previously row-click opened `EditorPane`. In M3.5, row-click opens `HabitScreen`. EditorPane is now reached only via the "Configure" button inside `HabitScreen`'s header. M3.4 keyboard shortcut for the editor (if any) preserved.

## 4. Architecture — VM topology

```
MainWindowViewModel  (existing, extended)
 ├── Home          (existing)
 ├── Settings      (existing)
 ├── Editor        (existing — M3.4)
 ├── HabitScreen   ← NEW
 │    ├── HeatmapViewModel        (90 cells, click to backdate)
 │    ├── QuickAddViewModel       (polymorphic per HabitType)
 │    ├── TimerControlViewModel   (start / pause / resume / stop, polls IActiveTimerService)
 │    └── CompletionListViewModel (recent N, paginated, edit/delete)
 └── TimerStatusBar ← NEW
      └── ActiveTimerRowViewModel[]  (one per active timer; 1s tick)
```

**Lifecycle:** `HabitScreenViewModel` is `Transient`; `MainWindowViewModel` keeps a single instance and calls `LoadAsync(habitNodeId)` whenever `Home.SelectedRow` changes (same pattern as `HabitEditorViewModel`). `TimerStatusBarViewModel` is `Singleton`; subscribes to `IEventBus` and refreshes its row list when active timers change.

## 5. Schema delta v2.5

### Table `active_timer`

| column | type | constraint |
|---|---|---|
| `id` | TEXT (Guid) | PK |
| `habit_node_id` | TEXT (Guid) | FK → `habit_node(id)` ON DELETE CASCADE; **UNIQUE** (at most one active timer per habit) |
| `started_at_ms` | INTEGER | Unix ms, non-null |
| `timer_mode` | TEXT | CHECK IN (`'Stopwatch'`,`'Countdown'`,`'Primary'`,`'Session'`) |
| `segment_index` | INTEGER | nullable; set only when `timer_mode='Session'` (current segment 0..N-1) |
| `paused_at_ms` | INTEGER | nullable; NULL means timer is running |
| `accumulated_paused_ms` | INTEGER | NOT NULL DEFAULT 0 — total ms spent paused across all pause cycles in this run |
| `created_at` | TEXT ISO 8601 | populated by `TimestampInterceptor` |
| `updated_at` | TEXT ISO 8601 | populated by `TimestampInterceptor` |
| `updated_at_ms` | INTEGER | LWW sync key |

Indexes:
- PK on `id`
- UNIQUE on `habit_node_id`

No `created_by_plugin_id` — timers are user/core-driven only.

- Create `active_timer` with the columns + unique constraint.
- Bump `AppSetting.schema_version` from `2.4` to `2.5`.

## 6. Quick-action icon per habit type

| HabitType | Icon (Lucide) | Click behaviour |
|---|---|---|
| Action | `check` | `ICompletionService.RecordAsync` with `CompletedAt=Clock.UtcNow`, no values, no segments. UI flashes the check ✓ for 1.5s. |
| Counter (no integrated timer) | `plus` | `RecordAsync` with one `CompletionValue` (`MetricDefinitionId` = first `MetricDefinition` by `SortOrder` ascending, `SeriesIndex=0`, `ValueInteger=1`). If the habit has no `MetricDefinition`, the quick-action falls back to creating a Completion with no values (effectively Action-like). |
| Counter (`HasIntegratedTimer=true`) | `play` | If no active timer → `IActiveTimerService.StartAsync`. If one is active → `StopAsync` then opens a small confirmation dialog showing the captured duration + a `Value` input. |
| Resistance | `play` | Same as Counter with timer (Resistance always has a timer per spec). |
| Journal | `pencil` | Opens `HabitScreen` AND focuses the quick-add `TextBox`. (The only icon-click that does not stay on Home.) |
| State | `chevron-down` | Opens an inline dropdown next to the icon listing the `ScaleTemplate` labels; selecting one writes a `Completion` with one `CompletionValue` (the integer code). |

Quick-icons live inside `HabitRowTemplate.xaml` and bind to commands on `HomeRowViewModel`:

```csharp
public IAsyncRelayCommand QuickActionCommand { get; }
```

`HomeRowViewModel` receives `IQuickActionHandler` (DI'd) to delegate the per-type behaviour. Groups have no quick-action icon.

## 7. Timer state machine

States: `Idle → Running ↔ Paused → Stopped (terminal)`.

Transitions invoked through `IActiveTimerService`:

```
StartAsync(habitId, mode)        : Idle    -> Running       (inserts active_timer row)
PauseAsync(habitId)              : Running -> Paused        (sets paused_at_ms = Clock.UtcNow)
ResumeAsync(habitId)             : Paused  -> Running       (adds Clock.UtcNow - paused_at_ms to accumulated_paused_ms, clears paused_at_ms)
StopAsync(habitId) -> Completion : Running -> Stopped       (deletes active_timer, builds + persists a draft Completion via CompletionService.RecordAsync)
                                   Paused  -> Stopped       (same; uses paused_at_ms as effective end)
NextSegmentAsync(habitId)        : Running (Session) -> Running (Session, segment_index+1). Caps at SegmentDefinition count; last next = Stop.
```

**Recovery on app start:** `ApplicationInitializer` (or a new `TimerRecoveryService`) reads every `active_timer` row, recomputes elapsed = `Clock.UtcNow - started_at_ms - accumulated_paused_ms - (Clock.UtcNow - paused_at_ms if paused)`, hands rows to `TimerStatusBarViewModel`. No user prompt — timers silently reattach.

**Sleep / system suspend:** out of scope. The persistence layer is enough — timers based on wall-clock arithmetic don't care about CPU sleep.

## 8. Validation rules

| Field / context | Rule |
|---|---|
| `Completion.CompletedAt` | `<= Clock.UtcNow` (no future). |
| `Completion.CompletedAt` for retroactive | `>= HabitNode.CreatedAt`. |
| `CompletionValue.MetricDefinitionId` | must reference a metric whose `HabitNodeId == Completion.HabitNodeId`. |
| `CompletionValue.SeriesIndex` | `>= 0`; within one `Completion`, the set of `(MetricDefinitionId, SeriesIndex)` is unique. |
| `CompletionValue` type fit | exactly one of `ValueInteger / ValueDecimal / ValueSeconds / ValueText` non-null, matching the `MetricDefinition.Type`. |
| `Journal Completion.Notes` | required, non-whitespace. |
| `IActiveTimerService.StartAsync` | throws `TimerAlreadyActiveException` if a row already exists for that habit. |
| `IActiveTimerService.PauseAsync` | no-op if already paused. |
| `IActiveTimerService.ResumeAsync` | no-op if already running. |
| Heatmap day click | date must be in `[HabitNode.CreatedAt.Date, Clock.UtcNow.Date]`. |

Existing per-type validation in `CompletionService.ValidatePerType` is preserved and extended (Resistance gets the same rule as Counter — at least one `CompletionValue`).

## 10. Acceptance criteria (mirror of CLAUDE.md §7 row 3.5)

1. **All five habit types record completions** via UI from Home: Action / Counter / Counter+session / Resistance / Journal / State.
2. **Multi-series completion** works for Counter/Resistance — user can add N series in one session (one Completion, N CompletionValues with SeriesIndex 0..N-1).
3. **Session mode** records a Completion with N CompletionSegment rows mirroring the SegmentDefinition list.
4. **Timer recovery**: kill the app while a timer is running → restart → timer is back, with elapsed matching wall-clock difference (± 1s).
5. **Retroactive entry**: click any past day on the heatmap → quick-add bound to that date → on save the Completion's `CompletedAt` is that day (with `IsRetroactive=true`).
6. **EventBus emit**: 3 event IDs registered in plugin contracts and emitted by `CompletionService` on Record / Update / Delete. Verifiable from a test handler.
7. **Multi-timer**: 2+ habits with active timers simultaneously → `TimerStatusBar` shows both, each with independent Pause/Stop.
8. **No hardcoded strings** — every label/error in `Strings.resx` (en) + `Strings.it.resx`.
9. **All VMs testable in isolation** — no WPF runtime required.
10. **Build clean, all tests green** before merge.

## 11. Known limits / deferred decisions

- **Streak engine** — not implemented; UI shows `—` placeholder. Event emit ready for M3.8.
- **Heatmap intensity** — binary or simple linear ramp by count. Per-metric weighted intensity is M3.7.
- **Bulk completion** — single-day click only.
- **Pause-on-system-suspend** — wall-clock arithmetic ignores CPU sleep; timers keep counting "real" elapsed.
- **Notification firing** — no scheduler in M3.5; rows persist but don't ring.
- **Markdown for Journal** — plaintext `TextBox` only; lift-and-replace by M3.6.
- **EditorPane discoverability** — old M3.4 row-click trigger removed. Users find Configure only inside HabitScreen. Acceptable trade because the design brief favours progressive disclosure of configuration.
- **Unique active timer per habit** — by design (no parallel timers on same habit). Different habits in parallel allowed.
- **Heatmap range fixed at 90 days** — chosen because the M3.3 HomeTreeRow already carries last-7-days. 90 days is the smallest range that visually shows weekly rhythm without paging. Bigger ranges deferred to M3.7.
