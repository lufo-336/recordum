# Milestone 3.2 — Core Data Layer + SQLCipher

> **Status**: design approved 2026-05-18 · **Phase**: 3 · **Predecessors**: [`2026-05-13-plugin-system-design.md`](../../specs/2026-05-13-plugin-system-design.md), [`2026-05-14-milestone-3.1-foundation.md`](../plans/2026-05-14-milestone-3.1-foundation.md)

## Goal

Stand up the production-grade core data layer on top of the Milestone 3.1 foundation:

- CRUD services for every user-facing top-level entity, with deterministic plugin provenance.
- Soft-delete cascade / restore / explicit purge on `HabitNode`.
- Automatic `HabitConfigHistory` snapshots via EF Core interceptor.
- Encryption at rest via SQLCipher, with `DpapiKeyProvider` (default) and `PassphraseKeyProvider` (opt-in Argon2id), plus a headless DPAPI ↔ passphrase transition service.
- Read-model query for the future Home Screen with an enforced p95 <300 ms budget.

This milestone ships no WPF UI beyond what 3.1 already has. Every capability is exercised via integration tests.

## Non-goals

- Settings UI for passphrase or trash management (3.3+).
- Background scheduler for purge (3.3+).
- `IResetTimeResolver` implementation, `StreakEngine`, `GoalProgress` computation (3.3 / 3.7 / 3.8).
- Note Markdown editor, Journal screen (3.6).
- Export execution, backup (3.10).
- Plaintext → encrypted DB migration path (no pre-3.2 users exist).
- Multi-user-on-same-machine, hardware-backed keys (TPM/YubiKey), key rotation, recovery codes.
- Plugin out-of-process runtime (Phase 7).

## 3. `HabitConfigHistoryInterceptor`

### 3.1 Trigger

`ISaveChangesInterceptor.SavingChangesAsync` — same extension point as the existing `TimestampInterceptor`.

### 3.2 Algorithm

For each `ChangeTracker.Entries<HabitConfig>()`:

1. If `entry.State == EntityState.Added` → no snapshot (no prior value to record).
2. If `entry.State ∈ { Modified, Deleted }`:
   - Read `entry.OriginalValues`.
   - Construct a `HabitConfigHistory` row mirroring all configurable columns **except** the non-versioned ones (per CLAUDE.md §5): `Id`, `HabitNodeId`, `CreatedAt`, `UpdatedAt`, `UpdatedAtMs`, `QuickComplete`, `AiDataSharing`, `ResetTime`.
   - Set `ValidFrom = OriginalValues.UpdatedAt`, `ValidUntil = clock.UtcNow`, `HabitConfigId = entry.Entity.Id`.
   - Add the new entity to the change tracker so it ships in the same transaction.

Each snapshot describes the half-open interval `[ValidFrom, ValidUntil)` during which those values were the truth. The first snapshot for a `HabitConfig` is written on the first modification after creation — not at creation.

### 3.3 Interceptor ordering

`HabitConfigHistoryInterceptor` must run **before** `TimestampInterceptor` so that the `OriginalValues.UpdatedAt` read by the history interceptor is still the pre-modification value. Registration order in `ServiceRegistrar` enforces this.

### 3.4 Hard-delete semantics

For `Deleted` entries the snapshot is still written. The `HabitConfigHistory` row records the final state of the configuration before it disappeared (e.g. via soft-delete cascade hard-deleting the parent `HabitNode` years later during purge). History rows are not cleaned up when the parent `HabitConfig` is hard-deleted — they remain a durable audit trail until the parent `HabitNode` is purged (see §4).

### 3.5 Resilience

- If `OriginalValues` is unexpectedly missing (EF bug), log a warning and skip — never abort the user's save.
- All snapshot rows are added inside the same EF `SaveChanges` transaction; failure rolls them back atomically.

### 3.6 Test obligations

- Single-field update → exactly one history row, snapshot mirrors prior state.
- Two sequential updates → two history rows with adjacent intervals.
- Modifying only excluded columns (e.g. `QuickComplete`) → no history row.
- `HabitConfig` hard-delete → final snapshot persisted.
- Save failure (forced via test-only failure) → no orphan history rows.
- Ordering check: `history.ValidFrom == oldEntity.UpdatedAt` (interceptor ran before `TimestampInterceptor`).

## 4. Soft-delete, restore, purge

### 4.1 `IHabitNodeService.SoftDeleteAsync(Guid habitNodeId)`

1. Load the node with `IgnoreQueryFilters`. If already soft-deleted, return (idempotent).
2. `deletedAt = clock.UtcNow` — a single timestamp shared by the entire subtree.
3. Discover descendants via a parameterised recursive CTE (`WITH RECURSIVE descendants AS …`). Faster than walking the tree with EF on deep hierarchies.
4. `UPDATE habit_node SET deleted_at = @deletedAt WHERE id IN (@subtreeIds)` inside a single transaction.
5. No explicit cascade on child entities (`Completion`, `Note`, `Goal`, …): the global query filter `HabitNode.DeletedAt IS NULL` already hides the entire subtree from default reads.

### 4.2 `IHabitNodeService.RestoreAsync(Guid habitNodeId)`

1. Load the node with `IgnoreQueryFilters`. If not soft-deleted, return (no-op).
2. Capture `tagDeletedAt = node.DeletedAt`.
3. Verify `node.Parent` is alive (`Parent == null || Parent.DeletedAt == null`). Otherwise throw `CannotRestoreOrphanException` — caller must restore the parent first.
4. `UPDATE habit_node SET deleted_at = NULL WHERE deleted_at = @tagDeletedAt AND id IN (@subtreeIds)` — exact-match on the timestamp. This ensures that descendants which were soft-deleted in *other* operations remain hidden.

### 4.3 `IPurgeService.PurgeExpiredAsync(TimeSpan olderThan)`

1. Candidates: nodes with `DeletedAt < clock.UtcNow - olderThan` (read with `IgnoreQueryFilters`).
2. For each candidate (one transaction per candidate node):
   a. Resolve file paths attached to descendants (future-proofing — none in 3.2).
   b. Delete in child→parent order: `Attachment` → `Note`; `CompletionValue` + `CompletionSegment` → `Completion`; `GoalProgress` → `Goal`; `MetricDefinition`; `Notification`; `StreakPause`; `HabitNodeTag`; `HabitConfigHistory` → `HabitConfig`; `SegmentDefinition`; then finally `HabitNode`.
   c. Commit DB transaction.
   d. Best-effort filesystem cleanup after commit. Filesystem errors are logged and reported in `PurgeReport.Errors` — they do not roll back the DB delete.
3. Returns `PurgeReport { Purged: int, Skipped: int, Errors: IReadOnlyList<PurgeError> }`.

### 4.4 Concurrency

All three operations open a fresh `DbContext` from `IDbContextFactory` and wrap their work in `BeginTransactionAsync()`. No shared context, no app-level locks — SQLite WAL + EF default retry policy is sufficient given the single-writer model.

### 4.5 Test obligations

- Soft-delete a 3-level tree → every node has `DeletedAt` set, normal queries hide them, `IgnoreQueryFilters` shows them.
- Soft-delete A, then separately soft-delete a child of A → restore A must not revive that child.
- Restore with soft-deleted parent → `CannotRestoreOrphanException`.
- `SoftDeleteAsync` on an already soft-deleted node → idempotent (no error, no extra rows).
- Purge ordering: child rows gone before parent row.
- Purge with simulated filesystem failure → DB commit still succeeds, error appears in report.
- Race between concurrent restore and purge on the same node → exactly one wins, no corrupted state.

## 5. SQLCipher, key providers, key transition

### 5.1 Native binding

Replace `SQLitePCLRaw.bundle_e_sqlite3` with `SQLitePCLRaw.bundle_e_sqlcipher` in `Recordum.Data.csproj`. The bundle ships the SQLCipher-enabled `e_sqlite3` native library and exposes the standard `PRAGMA key` / `PRAGMA rekey` API.

### 5.2 `IDbKeyProvider`

```csharp
public interface IDbKeyProvider
{
    string ProviderId { get; } // "dpapi" | "passphrase"
    ValueTask<KeyMaterial> GetKeyAsync(CancellationToken ct);
}

public sealed record KeyMaterial(byte[] RawKey) : IDisposable
{
    public void Dispose() => CryptographicOperations.ZeroMemory(RawKey);
}
```

`KeyMaterial.RawKey` is 32 bytes. Callers `using`-scope the value so the buffer is zeroed when the operation completes.

### 5.3 `DpapiKeyProvider`

- On first call: if `%LocalAppData%/Recordum/db.key` is missing, generate 32 random bytes (`RandomNumberGenerator.Fill`), protect with `ProtectedData.Protect(key, entropy: null, DataProtectionScope.CurrentUser)`, write to the file with exclusive permissions.
- On subsequent calls: read file, `ProtectedData.Unprotect`, return `KeyMaterial`.
- Throws `KeyUnavailableException` if the file exists but cannot be decrypted (different OS user, corrupted).

### 5.4 `PassphraseKeyProvider`

- Constructed with a passphrase (`SecureString`-style handling: `string` accepted but never logged; stored on the provider instance, not persisted).
- Salt: 16 random bytes persisted to `%LocalAppData%/Recordum/db.salt`. The salt is created during DPAPI → passphrase transition (§5.6). Salt is not a secret.
- KDF: Argon2id via `Konscious.Security.Cryptography.Argon2`. Parameters:
  - `Iterations = 4`
  - `MemorySize = 65_536` (64 MiB)
  - `DegreeOfParallelism = 2`
  - Output length: 32 bytes.
- Throws `KeyUnavailableException` if the salt file is missing (= no passphrase was ever configured for this DB). A wrong passphrase is detected indirectly: SQLCipher fails to open the DB on the derived key.

Minimum passphrase length: 12 characters. No complexity check beyond length — the Settings UI (3.3+) will surface guidance and warnings about data loss.

### 5.5 Bootstrap integration

`ApplicationInitializer.InitializeAsync`:

1. Resolve `IDbKeyProvider` from DI (default registration: `DpapiKeyProvider`).
2. Acquire `KeyMaterial` via `await provider.GetKeyAsync(ct)`.
3. Build a `SqliteConnection`, open it, then execute `PRAGMA key = "x'<hex>'"` as the very first statement, before any schema operation.
4. Pass the open connection to `RecordumDbContext` via `DbContextOptionsBuilder.UseSqlite(connection)`.
5. Run pending migrations.
6. Smoke-check the plugin manager (existing 3.1 behaviour).
7. `KeyMaterial.Dispose()` zeroes the buffer.

`SqlCipherConnectionFactory` (in `Recordum.Data/Security/`) encapsulates step 3 so the same logic is reused by tests and by the transition service.

### 5.6 `IKeyTransitionService`

```csharp
public interface IKeyTransitionService
{
    ValueTask TransitionToPassphraseAsync(string newPassphrase, CancellationToken ct);
    ValueTask TransitionToDpapiAsync(string currentPassphrase, CancellationToken ct);
}
```

#### `TransitionToPassphraseAsync`

1. Pre-flight: passphrase length ≥ 12, not whitespace-only.
2. Take a file copy of `recordum.db` to `recordum.db.bak.<ticks>`.
3. Open DB with the current DPAPI key.
4. Generate 16 random bytes for the new salt; derive the new key via Argon2id.
5. Run `PRAGMA rekey = "x'<newhex>'"` — SQLCipher performs the rekey atomically.
6. Write the new salt file `%LocalAppData%/Recordum/db.salt`.
7. On success: delete the DPAPI key file `db.key`. Delete the backup.
8. On failure: restore the backup over `recordum.db`, leave `db.key` intact, throw `KeyTransitionFailedException(inner)`. Salt file is not written.

`TransitionToDpapiAsync` is the symmetric inverse: rekey back, generate new DPAPI-protected `db.key`, delete `db.salt`.

### 5.7 Test obligations

- Fresh start with DPAPI → DB encrypted; deleting `db.key` and reopening → `KeyUnavailableException`.
- DPAPI → passphrase: rekey succeeds, reopen with passphrase succeeds, reopen with DPAPI fails.
- Passphrase forgotten → DB inaccessible (this test documents the "no recovery" invariant).
- Rekey interrupted mid-operation (simulated via a fault-injecting wrapper): backup restored, DB still openable with the original DPAPI key, no salt file written.
- `KeyMaterial.Dispose()` → underlying buffer is zeroed.

## 6. Performance budget

### 6.1 Seeded dataset

`PerfDataSeeder` in `Recordum.Data.Tests/Performance` produces a deterministic dataset (`Random(seed: 42)`):

- 200 `HabitNode` distributed across 30 hierarchical groups (max depth 3).
- Habit-type mix: 80 action, 60 counter, 30 resistance, 20 journal, 10 state.
- 50,000 `Completion` rows spread over the last 12 months (~250 per habit on average, with a long tail at 1,000+ for the busiest).
- 5,000 `Note` rows, 100 `Goal` rows, 50 `MetricDefinition` rows.

This is the "advanced user, multi-year" envelope. If real-world telemetry in later phases shows a different distribution, the seeder updates and the budget is re-asserted.

### 6.2 Budget assertion

```csharp
[Fact]
[Trait("Category", "Performance")]
public async Task GetHomeTreeAsync_p95_under_300ms()
{
    // … fixture + seed …

    // Warm-up
    for (int i = 0; i < 3; i++) await query.GetHomeTreeAsync();

    var samples = new List<long>();
    for (int i = 0; i < 20; i++)
    {
        var sw = Stopwatch.StartNew();
        await query.GetHomeTreeAsync();
        samples.Add(sw.ElapsedMilliseconds);
    }
    samples.Sort();
    var p95 = samples[(int)(samples.Count * 0.95)];
    Assert.True(p95 < 300, $"p95={p95}ms exceeds 300ms budget. samples=[{string.Join(",", samples)}]");
}
```

Failure messages include the full sample array so a regression vs. a transient spike is distinguishable.

### 6.3 SQLCipher overhead test

A companion test (`SqlCipherOverheadBenchmark`) measures the same query on an encrypted file vs. a plaintext file and asserts overhead ≤ 30 %. This guards against accidental regressions in the encryption path (e.g. missed `PRAGMA cipher_page_size` tuning).

### 6.4 Query shape

`GetHomeTreeAsync` returns a flat list of `HomeTreeRow` records:

```csharp
public sealed record HomeTreeRow(
    Guid HabitNodeId,
    Guid? ParentId,
    string Name,
    string ColorHex,
    HabitType HabitType,
    DateTime? LastCompletionAt,
    int CurrentStreakCount,
    bool IsCompletedToday);
```

Implementation uses a single SQL query: tree projection + correlated subquery for `LastCompletionAt` + denormalised streak read (streak engine arrives in 3.8; in 3.2 `CurrentStreakCount` reads from the existing `Streak` column maintained by manual updates in tests). Required index `(habit_node_id, completed_at_ms DESC)` on `Completion` is already declared in 3.1.

## 7. Plugin provenance & context

### 7.1 Scope discipline

All services are scoped. The host opens a DI scope per logical operation. `IPluginContext` lives in that scope.

- **User-driven code (UI/ViewModels)**: uses the root scope's `NullPluginContext` (`PluginId == null`). Entities written here get `CreatedByPluginId = null`.
- **Plugin-driven code**: `PluginManager.InvokeAsync(pluginId, async sp => …)` opens a scope where `IPluginContext.PluginId == pluginId` and resolves services from `sp`. All writes inside the scope inherit `pluginId`.

### 7.2 Provenance population

Four services populate `CreatedByPluginId` from `IPluginContext.PluginId` on `CreateAsync`: `HabitNodeService`, `HabitTemplateService`, `ChartService`, `ExportTemplateService`. Updates do not touch the column — provenance is immutable.

Child / non-provenance entities (`Completion`, `Note`, `Goal`, `GoalProgress`, `MetricDefinition`, `Notification`, `Tag`, `StreakPause`) do not carry the column and ignore `IPluginContext`.

### 7.3 Interceptor scope resolution

The existing `TimestampInterceptor` is singleton-scoped and resolves `IPluginContext` via `IServiceProvider` at save-time (not at construction). Milestone 3.2 verifies this works inside a plugin-invoked scope via a `FakePluginContext`. If the current 3.1 wiring captures `IPluginContext` at construction (bug), it is fixed as part of 3.2.

### 7.4 Extension points

The 3.1 plugin foundation already registers extension-point IDs for `data.before-save` / `data.after-save` / `data.query-extension`. Milestone 3.2 does **not** consume them. First-party consumers arrive with the Chart Engine (3.9) and Export (3.10). The infrastructure is intentionally left dormant.

## 9. Error model

All domain exceptions derive from `RecordumDomainException` (new base type in `Recordum.Core.Errors`):

| Exception | Thrown by | Carries |
|---|---|---|
| `HabitNodeNotFoundException` | `IHabitNodeService.UpdateAsync/MoveAsync/SoftDeleteAsync/RestoreAsync` | `Id` |
| `HabitNodeAlreadySoftDeletedException` | `Update`, `Move` on a soft-deleted node | `Id` |
| `CannotRestoreOrphanException` | `RestoreAsync` when parent is soft-deleted | `Id`, `ParentId` |
| `CyclicHabitNodeMoveException` | `MoveAsync` when new parent is in the subtree | `Id`, `NewParentId` |
| `InvalidCompletionForHabitTypeException` | `ICompletionService` | `HabitNodeId`, `HabitType`, `Reason` |
| `KeyUnavailableException` | `IDbKeyProvider` impls | `ProviderId`, `Reason` |
| `KeyTransitionFailedException` | `IKeyTransitionService` | `FromProvider`, `ToProvider`, `InnerException` |

UI mapping (3.3+) is out of scope here. Logging guidance is in §10.
