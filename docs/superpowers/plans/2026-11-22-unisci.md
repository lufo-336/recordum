# "Unisci" (computer) — piano di implementazione

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or
> superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** più computer convergono allo stesso stato scambiandosi un file `.rcsync` per dispositivo in una cartella
sincronizzata, senza perdere niente e senza far tornare ciò che è stato cancellato.

**Architecture:** un **catalogo** (`SyncCatalog`) dice cosa viaggia e con quali nomi pubblici; il resto è generico e
guidato dai metadati EF. Il database cattura ore di modifica e cancellazioni con **trigger** che leggono `IClock` da
una funzione SQLite registrata per connessione. Il file è uno ZIP di JSON Lines + foto dentro la busta AES-GCM dei
backup con magic `RCSY`. Il motore unisce riga per riga con una **base** per peer, in una transazione, con i trigger
spenti mentre applica.

**Tech Stack:** .NET 10, EF Core 10, SQLite3MC (formato SQLCipher 4), `System.IO.Compression`, `System.Text.Json`,
Avalonia 12, xunit (v3 in `Recordum.UI.Tests`).

**Spec:** `docs/superpowers/specs/2026-11-22-unisci-design.md` (approvata il 2026-11-22). Sonda:
`docs/design/2026-11-22-saf-drive-probe.md`.

**Fuori da questo piano:** il telefono (implementazione SAF di `ISyncFileStore` e righe "Dove sono i file" del
telefono) — piano a parte dopo la testa Android (ROADMAP passo 4). Il collegamento diretto a Drive. Export/Import.

## Global Constraints

- Mai `DateTime.UtcNow/Now`: il tempo da `IClock` (`UtcNowMs` per gli `*_ms`). Nei trigger, mai l'orologio di SQLite.
- `Recordum.Presentation` resta `net10.0` senza `-windows`; un ViewModel non tocca l'host se non via astrazione.
- Ogni stringa utente in `Strings.resx` + `Strings.it.resx` + accessor in
  `src/Recordum.Presentation/Resources/Strings.Designer.cs` (**solo via shell**: l'hook blocca Edit/Write sui
  `*.Designer.cs`). Ogni voce di Impostazioni › Unisci ha una riga di spiegazione.
- Migrazione: `dotnet ef migrations add <Nome> --project src/Recordum.Data --startup-project src/Recordum.Data`;
  `#pragma warning disable CA1861` dopo `#nullable disable`; mai editare `*.Designer.cs`/`*ModelSnapshot.cs` di EF.
  Il bump a **2.21** tocca gli 8 riferimenti a `"2.20"` nei test (nomi dei metodi compresi).
- `TreatWarningsAsErrors` globale; versioni esatte in `Directory.Packages.props`; **nessun pacchetto nuovo**.
- File in chiaro dell'unione solo in `TempDirectory` (`SystemTempGuardTests`); lo ZIP in chiaro solo dove lo sceglie
  l'utente.
- Il formato è un contratto: `format = "recordum-sync"`, `format_version = "1.0"`; nomi pubblici `snake_case` inglesi
  congelati nel catalogo; un campo assente non è null né cancellato; maggiore diversa = rifiuto.
- Magic della busta `RCSY`; `RCBK` dei backup invariato (i test dei backup restano verdi senza modifiche).
- Avalonia: `InitializeComponent()`, `x:DataType` ovunque, `[AvaloniaFact]`, `RunJobs()` + `ForceRenderTimerTick()`,
  un PNG va con un'asserzione strutturale.
- Linux: `dotnet test … --filter "Category!=WindowsOnly"`; filtri per **nome di classe** e controllo del totale.
- Lavoro sul branch `unisci` da `main` (non su `unisci-spec`); commit per task; push e CI dopo ogni gruppo.

## Review Focus

1. **Un file del peer troncato, a metà caricamento o modificato a mano male** (JSON rotto dopo "Ricifra"): il giro lo
   salta senza applicarne nemmeno una riga e lo stato lo dice in parole. → Task 4 (busta), Task 5 (JSON rotto), Task 9.
2. **Crash o chiusura durante un giro**: il DB resta com'era (transazione) e il proprio file resta quello di prima
   (scrittura su temporaneo + rinomina). → Task 9.
3. **Due file con lo stesso `device_id`** (DB copiato su un'altra macchina senza ripristino): nessuna unione con quel
   file, stato "due dispositivi con la stessa identità". → Task 9.
4. **Orologio di un dispositivo sbagliato di ore**: i numeri possono cambiare vincitore, ma **nessun testo si perde**
   (la regola B scatta comunque). → Task 7.
5. **File grande con tante foto**: scrittura e lettura in streaming delle foto, senza tenerle tutte in memoria. →
   Task 5 (test `Category=Performance`, locale).

### Task 6: Il motore d'unione — righe, lapidi, base

**Livello:** Opus.

**Files:**
- Create: `src/Recordum.Data/Sync/SyncMerger.cs`, `src/Recordum.Data/Sync/SyncMergeReport.cs`
- Test: `tests/Recordum.Data.Tests/Sync/SyncMergerTests.cs`, `tests/Recordum.Data.Tests/Sync/SyncConvergenceTests.cs`,
  `tests/Recordum.Data.Tests/Fixtures/Sync/SyncDevice.cs` (un `DbFixture` con nome, `device_id`, `FakeClock` proprio,
  `WriteFile()` → byte cifrati, `Merge(bytes)`, `CanonicalDump()` = tutte le righe pubbliche ordinate + lapidi)

**Interfaces:**
- Consumes: `SyncSnapshot` (Task 5), `SyncConnectionState` (Task 3), `SyncBase`/`SyncTombstone` (Task 2).
- Produces:
  - `SyncMerger.MergeAsync(RecordumDbContext db, SyncSnapshot remote, string localDeviceId, bool receivePhotos, CancellationToken ct) : Task<SyncMergeReport>`
  - `public sealed record SyncMergeReport(int Inserted, int Updated, int Deleted, int TextConflicts, int Repaired)`
- Algoritmo (in una transazione; `Applying = true`; `PRAGMA defer_foreign_keys = ON` così l'ordine di inserimento non
  conta):
  1. Lapidi remote: per ognuna, se la riga locale ha `updated_at_ms` > `deleted_at_ms` la riga vince (e la lapide
     **non** si copia); altrimenti si cancella la riga (le cascade locali seguono) e si scrive la lapide con il
     `deleted_at_ms` remoto (`INSERT OR REPLACE` se più recente).
  2. Righe remote: id con lapide locale più recente di `updated_at_ms` remoto → ignorata. Id sconosciuto → insert.
     Id noto → per campo: `local≠base` e `remote=base` → locale; `local=base` e `remote≠base` → remoto; entrambi
     diversi → vince la riga con `updated_at_ms` maggiore; a parità, la riga con JSON canonico minore
     (deterministico). Senza base: confronto di riga intera con la stessa regola. `updated_at_ms` risultante =
     massimo dei due.
  3. Storici (`IsHistory`): solo insert di righe nuove.
  4. `receivePhotos = false`: le colonne `Photo` remote non si scrivono e una foto locale senza originale non si
     considera cambiata.
  5. Aggiornare `sync_base` per (peer, entità, id) con la riga **remota** in forma pubblica.
